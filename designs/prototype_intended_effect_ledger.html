Intended Effect & the Considered-and-Dropped Ledger

The question this demo pushes on: ADR-0030 adds "intended effect" — a free-text note of what the customer wants done to the radio wave (absorbed, reflected, transmitted...) — as a key on a Customer requirement, specifically so the Considered-and-dropped ledger (which design families got tried and rejected, and why) becomes comparable across designs. Grilling that decision surfaced four open questions about the state model:

  1. Q1 — one ledger reason, capability-verdict, was being asked to mean two things that expire on two different triggers (shop equipment vs. a requirement's own curvature). Resolved while prototyping: equipment/inventory unavailability is a warning, never a reason to drop a candidate — the charter says present equipment "shape[s] the ranking and the warnings, never the search." So capability-verdict now only ever means "outside this element's characterized validity box" (e.g. curvature) — a genuine exclusion, not a supply problem. The sub-field question disappears because the ambiguity it was solving no longer exists.
  2. Q2 — intended effect is deliberately free text with no closed list. Does a soft, suggestion-only "house style" registry actually stop two designs asking for the same thing from becoming invisible to each other — or does typing something slightly different still break it?
  3. Q3 — should the system refuse to run the ARCHITECTURE step (where the ledger gets written) until every requirement has a stated intended effect, the same way it already refuses without a stated design family?
  4. Q4 — if a customer wants two different things at once, does forcing that into two requirement rows (rather than a list on one row) actually hold up, or does the model let someone cram two wishes into one label anyway?

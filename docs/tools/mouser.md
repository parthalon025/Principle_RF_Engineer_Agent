# Mouser Search API

Mouser Electronics is an authorized distributor of electronic components — a
company that buys real inventory directly from manufacturers and resells it —
and its Search API is the programmatic front door to that catalog: give it a
part number or keyword, and it answers whether Mouser stocks the part, what
it costs at various order quantities, and where to fetch its datasheet PDF.
This repo uses it as one of three "component-sourcing" tools (alongside
Digi-Key and Nexar/Octopart) so that once the model proposes a physical part
— a substrate, an RF connector, a lumped element — it can check the part is
real and pull its datasheet as cited evidence, instead of trusting the
model's memory of a part number that may not exist.

## What it is

Mouser Electronics, headquartered in Mansfield, Texas, is a global
authorized distributor for over 1,200 manufacturer brands [1][2]. "Mouser
APIs" is the umbrella name for the company's own machine-readable interface
to that catalog, described in its own OpenAPI (Swagger) specification as
giving "quick and reliable access to product data as well as cart and
ordering capabilities" [3]. Two API generations are live side by side, V1
and V2 — V2 only replaces three V1 search endpoints that V1 itself marks
deprecated, so in practice the two form one current surface, generated by
the ASP.NET tool "Swagger.Net" version 8.5.12.001 [3][4]. There is no
separate open-source client library or GitHub repo for the API itself (it is
Mouser's own hosted service, closed-source); community wrapper packages
exist in Python, TypeScript and Go but are third-party, unofficial, and
unaffiliated with Mouser [5][6][7].

## Full capabilities

Fetched directly from Mouser's own OpenAPI spec at `api.mouser.com/api/docs/V1`
and `/V2` — the interactive Swagger UI page renders that same spec via
JavaScript this session cannot execute, but the underlying JSON files it
fetches are reachable directly [3][4] — the Search API is only one of four
service groups under one umbrella key: **Search** (`search/keyword`,
`search/partnumber`, `search/keywordandmanufacturer`,
`search/partnumberandmanufacturer`, `search/manufacturerlist`), **Cart**
(get/replace cart, insert/update/remove items, insert/update/delete
scheduled deliveries), **Order History** (by date filter, date range, sales
order #, web order #), and **Order** (query shipping/payment/tax options,
currencies, countries, submit or clone an order, fetch order details, build
a cart from a past order) [3][4]. A part-number search returns up to 50
parts per call (10 pipe-delimited part numbers per request, 3-40 characters
each); each returned `MouserPart` carries `Availability`, `LeadTime`,
`PriceBreaks` (quantity/price/currency tiers), `StandardCost`,
`ROHSStatus`/`REACH-SVHC` compliance flags, `ProductCompliance`/
`TradeCompliance` (export-control), `AlternatePackagings`, and
`ProductDetailUrl`/`DataSheetUrl`, not just identity fields [3]. The spec
also resolves a gap this repo's own adapter had flagged as unverified: the
`partSearchOptions` request field's valid values are exactly `"None"` and
`"Exact"` [3].

## Integrations & interfaces

Auth is a single `apiKey` query-string parameter on every call — confirmed
directly in the spec's own parameter list for `POST
/api/v{version}/search/partnumber` [3] — not OAuth2 like Digi-Key or Nexar.
Mouser actually issues two separate keys, one for Search and one for
Cart/Order, per a third-party wrapper's README [5]; the search-only key this
repo requests cannot place an order even if the code were extended to call
those endpoints. Registration is a free "My Mouser" account, with key
approval taking roughly 1-2 business days rather than being instant [8].
Mouser does not publish a numeric rate-limit cap the way Digi-Key does
(Digi-Key states 120 requests/minute in its own docs, per this repo's
`docs/tools/digikey.md`); third-party integrators instead advise treating
about 30 requests/minute as a safe informal ceiling and note the API returns
HTTP 429 once exceeded [8] — **this could not be corroborated against
Mouser's own docs**, since `mouser.com/en/apiterms/`,
`/en/api-hub/`, `/en/api-search/`, `/en/aboutus/`, and the
`pdfDocs/api-guide.pdf` guide all returned an "Access to this page has been
denied" bot-block page to both WebFetch and a direct browser-header `curl`
in this session — the same inaccessibility this adapter's own module
docstring already reported. Cost is a free tier with no subscription fee;
use of returned data is subject to Mouser's own proprietary API terms, not
an OSI license, per this repo's existing `docs/LICENSE_MATRIX.md` (itself
citing the now-inaccessible terms page).

**Vs. the other two component-sourcing tools:** Digi-Key layers OAuth2 plus
a required `X-DIGIKEY-Client-Id` header and publishes numeric rate caps [9];
Nexar/Octopart aggregates *multiple* distributors (Mouser included) behind
one GraphQL query with a free tier capped near 1,000 matched parts. Mouser
sits in between — simpler flat-key auth, no published cap — but returns only
Mouser's own stock and pricing, a single distributor's direct view rather
than a cross-distributor rollup.

## How this repo uses it today

`knowledge/mouser.py`'s `lookup_mouser_datasheet()` calls exactly one
endpoint: `_search_by_part_number()` POSTs to `search/partnumber` with
`{"SearchByPartRequest": {"mouserPartNumber": <part>, "partSearchOptions":
"None"}}`. `_parse_matches()` reads only `ManufacturerPartNumber`,
`Manufacturer`, and `DataSheetUrl` off the **first** returned part, discarding
`Availability`, `PriceBreaks`, `LeadTime`, `StandardCost`, and every
compliance field the same response already carries. The matched datasheet
URL is downloaded and handed unchanged to
`knowledge.ingest.ingest_document(source_type="datasheet")`. The whole call
is refused unless `ALLOW_EXTERNAL_NETWORK_TOOLS=true`
(`knowledge/sourcing_common.py`), and `get_api_key`/`search`/`download`/
`ingest` are all injectable so `tests/test_mouser.py` exercises the
argument-passing and response-parsing logic against a canned response with
no live `MOUSER_API_KEY` or network access — the module's own docstring is
explicit that it has never been run against the real API end-to-end.

## Capabilities not yet used here

- **Pricing, availability, and lead-time fields** (`PriceBreaks`,
  `Availability`, `LeadTime`, `StandardCost`) are already returned by the
  one call this repo makes but are dropped in `_parse_matches()`. This is
  the most useful gap for this repo's own stated purpose: CLAUDE.md names
  design-for-manufacture as the destination, and a part that is out of
  stock or on a 52-week lead time is a materially worse candidate — data
  already in hand, at zero extra API cost, that never reaches scoring.
- **Compliance flags** (`ROHSStatus`, `REACH-SVHC`, `ProductCompliance`,
  `TradeCompliance`/export-control) — relevant to whether a proposed part is
  legally buildable/shippable for a given program, unused.
- **`search/keyword`** — lets the model search by a loose description (e.g.
  "flexible magnetic absorber sheet") when it has no exact part number yet;
  today the adapter only supports exact part-number lookup.
- **`search/partnumberandmanufacturer`/`keywordandmanufacturer`** (V2) — can
  disambiguate a part number reused across multiple manufacturer brands,
  which plain part-number search cannot.
- **Cart and Order service groups** — genuinely unused, and correctly so:
  those endpoints place real orders, which is exactly the one hard stop this
  program keeps (nothing spends real money without a human saying yes). Their
  absence here is the right call, not a missed integration, and the separate
  cart/order API key this repo never requests keeps that boundary enforced
  at the credential level, not just in code.

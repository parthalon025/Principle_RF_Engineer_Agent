# Digi-Key Product Information API v4

Digi-Key is an electronic-component distributor — a warehouse-and-catalog company, not a simulator — and its Product Information API v4 is the programmatic front door to that catalog: given a manufacturer's part number, it returns whether Digi-Key stocks the part, at what price, and where to get the datasheet. This repo uses it as one of three "component-sourcing" tools (alongside Mouser and Nexar) to close the last mile of a design: once the model has proposed a physical part (a substrate, an RF connector, a lumped element), this API is how it checks that the part is real, in stock, and has a datasheet to ingest as evidence — rather than trusting the model's memory of a part number that may not exist.

## What it is

A REST/JSON API suite published and operated by Digi-Key Corporation (Thief River Falls, MN) at `developer.digikey.com`, requiring a free "My DigiKey" account and OAuth 2.0 registration [developer.digikey.com]. It sits alongside DigiKey's older v3 APIs, which the portal is actively migrating customers off of, making v4 the current, maintained surface. Use of the API and any data it returns ("DigiKey Data") is governed by DigiKey's own API User Agreement plus its site-wide Terms & Conditions — a distributor's data-use contract, not an open-source license [developer.digikey.com/api-user-agreement].

## Full capabilities

The Product Information v4 "ProductSearch" service alone exposes thirteen-plus endpoints, not just keyword search: `KeywordSearch` (POST, broad text/MPN search, no pricing), `ProductDetails` and `ProductPricing` (GET, full record for one matched part including "MyPricing" contract pricing), `PricingOptionsByQuantity`, `PackageTypeByQuantity` (deprecated in favor of the former), `Manufacturers`, `Categories`/`CategoriesById`, `Media` (datasheets, images, other documents for a part), `AlternatePackaging`, `DigiReelPricing` (DigiKey's own custom-reel repackaging service), `RecommendedProducts`, `Substitutions`, and `Associations` (accessory/mating parts) [developer.digikey.com/products/product-information-v4/productsearch]. Beyond product information, the wider DigiKey API portal also offers Quoting, Order Placement, Order Status/Management, MyLists, Supply Chain Inventory (bonded/consigned stock locations), Product Change Notifications (part obsolescence/revision alerts), and Barcode Identification APIs [developer.digikey.com]. Rate limits are set per API product: Product Information, Order Support and Barcode are each capped at 120 requests/minute and 1,000/day; Quoting, Ordering and BOM-creation are capped at 10/minute with no daily cap; every response carries `X-RateLimit-*`/`X-BurstLimit-*` headers, and exceeding a cap returns HTTP 429 with `Retry-After` [developer.digikey.com/tutorials-and-resources/shared-concepts; corroborated at forum.digikey.com/t/digikey-api-rate-limit-increase/21539].

## Integrations & interfaces

Plain HTTPS REST, JSON in and out, over TLS 1.2 [developer.digikey.com/tutorials-and-resources/shared-concepts]. Auth is OAuth 2.0 client_credentials ("2-legged flow") for machine-to-machine product lookups, documented separately from a 3-legged authorization-code flow used where the call acts on a person's own MyDigiKey account (orders, lists) [developer.digikey.com/tutorials-and-resources/oauth-20-2-legged-flow]; one shared-concepts page states authorization-code is "the only permitted way of accessing DK APIs," which reads in tension with the dedicated 2-legged-flow tutorial — noted here rather than resolved, since neither page was itself run against a live token exchange. Every environment (sandbox at `sandbox-api.digikey.com`, production at `api.digikey.com`) is registered the same way, differing only by hostname; access tokens last roughly 10 minutes.

## Licensing & cost

No published subscription price was found. Standard API access — the tier this repo's adapter uses — appears to be free once a My DigiKey account is registered and the API User Agreement accepted, capped at 1,000 searches/day; higher volume needs sales-manager approval, and a DigiKey Credit Account is required before any order-placing endpoint can be used [digikey.com/en/resources/api-solutions-faqs]. "Enhanced-access feed" APIs and displaying DigiKey Data on any downstream site both require separate written approval via `api.contact@digikey.com` [developer.digikey.com/api-user-agreement].

## How this repo uses it today

`knowledge/digikey.py`'s `lookup_digikey_datasheet()` calls exactly one endpoint — `KeywordSearch` (`POST /products/v4/search/keyword`, `{"Keywords": part_number}`) — takes the first returned match, and if it carries a `DatasheetUrl` downloads that PDF and hands it to `knowledge/ingest.py`'s existing `ingest_document(source_type="datasheet")` pipeline. `_parse_matches` reads `Products[].Manufacturer.Name` / `.ManufacturerProductNumber` / `.DatasheetUrl`, an assumption inferred from the `digikey-apiv4` PyPI client's attribute names rather than a live response, and the module's own docstring flags this as unverified end-to-end (no `DIGIKEY_CLIENT_ID`/`SECRET` registered here). It gates on `ALLOW_EXTERNAL_NETWORK_TOOLS=true` and is fully dependency-injected for testing. No availability, category, or ordering endpoint is called.

**Since ticket #275** (closing the exact gap this report first flagged below), the module also has `lookup_digikey_product_details()`, calling `ProductDetails` (`GET /products/v4/search/{productNumber}/productdetails`) and parsing its `Product.Parameters[]` (generic per-category parametric attributes — frequency range, impedance, tolerance, or whatever that part's category actually names them) and its `Product.ProductVariations[0].StandardPricing`/`.MyPricing` (list and contract price/quantity breaks) into a structured result — one call, zero additional API cost, mirroring the "data already fetched but discarded" shape of Mouser's own #274 fix. `developer.digikey.com`'s own `ProductDetails` page turned out to be a JS-rendered nav shell with no schema body (confirmed by a live fetch attempt for #275); the field names above are corroborated instead from `Innovoltive/digikey_apiv4`, a swagger-codegen-generated third-party client (same evidentiary tier as the `digikey-apiv4` citation above). That research also turned up a discrepancy with this report's own "Full capabilities" section below: the corroborating client's method list has no distinct `product_pricing` method at all — `product_details` is documented as already returning "real time pricing," and #275's implementation trusts that over this report's now-unconfirmed claim of a separate `ProductPricing` endpoint. See `knowledge/digikey.py`'s module docstring for the full citation trail.

## Capabilities not yet used here

`Substitutions`/`RecommendedProducts`/`Associations` (alternate-part discovery when the first match is out of stock or discontinued), `Categories` (browsing RF-connector/filter/substrate categories rather than exact-MPN lookup only), and `Product Change Notifications` (obsolescence tracking for a part a design has committed to) are all unused. `PricingOptionsByQuantity`/`PackageTypeByQuantity` (pricing broken out by a caller-chosen order quantity, rather than the full tiered `StandardPricing` table #275 now returns) remain unused too — a smaller gap than before, not a new one. Ordering/Quoting/Supply Chain endpoints exist but would need explicit gating to respect this repo's "nothing that spends money without a human yes" rule before any adapter called them.

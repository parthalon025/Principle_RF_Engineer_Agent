# Design family keeps both the caller's spelling and the registry's canonical name

`orchestration/design_loop.py`'s ARCHITECTURE step already resolves a stated `design_family` against `designs/design_families.py`'s registry and computes a canonical payload (`recorded["design_family_registry"]`, including `canonical_name`) specifically so two callers who spell the same family differently ("patch_antenna" vs "PATCH") still group together for the not-yet-built #150/#151. The code's own comment gives the reasoning: normalizing the caller's own field in place would mean "a decision record that quietly rewrites what they wrote," which is worse than carrying a second field.

**Decision**: `decision_records` persists both values, never merged into one — the caller's exact spelling (`design_family`, never rewritten) and the registry's canonical name alongside it. #150/#151 and any other cross-run grouping query read the canonical value; anything that cares what a human or agent actually typed reads the raw one. This is the same instinct this codebase applies everywhere else it draws a "what was said" vs. "what it resolves to" distinction (e.g. Intended effect vs. Design family itself, or a Requirement target's `ASSUMED` provenance surviving confirmation on a separate status axis rather than being overwritten).

**Consequences**: a reader who groups by `design_family` alone will still fragment on spelling variants — the canonical field, not the raw one, is what backs cross-run grouping. `design_family_registry`'s canonical payload was already being computed at ARCHITECTURE time before this decision; the gap this closes is that `orchestration/tooling.py`'s flush path only ever read `design_family` (raw) out of `decision.input`, silently dropping the canonical payload before it ever reached Postgres — `db/schema.sql` had exactly one column for it. The fix threads the already-computed canonical name through the flush boundary into a companion column, rather than computing it a second time on read.

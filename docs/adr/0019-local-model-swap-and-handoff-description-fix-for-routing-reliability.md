# Multi-agent routing reliability: a clean model tag, uniform `_ROUTING_SUMMARY` handoff descriptions, and a role-neutral shared prompt

Bringing the Dockerized solver stack up against a real local Ollama backend (not the mocked/no-credential path `tests/test_agent_roles.py` is limited to) reproduced a live, repeatable failure in the principal role's multi-agent routing in `agent/main.py`: a multi-turn tool-calling exchange crashed with `openai.InternalServerError: 500 – "no user query found in messages"` (a 500 is the server telling the client "I broke," not "your request was bad"). Chasing that crash to ground surfaced three separate, compounding problems, not one:

1. The local model tag, `qwen3.8:27b`, has a confirmed, currently-unpatched Ollama bug that produces exactly this crash on any multi-turn tool-calling exchange over `/v1/chat/completions` — the OpenAI-wire-shaped endpoint (a REST API shaped like OpenAI's own, so any OpenAI-client library can talk to it) that this repo's `openai-agents` SDK always uses, regardless of provider.
2. Even past that crash, the principal could not reliably choose *which* specialist to hand a question to. Each of the five `route_to_<role>_role` handoffs' tool-selection description (the text a model reads to decide which tool fits a request) was that specialist's own `domain_note` — verbatim, second-person text written as that specialist's *internal* instructions for its own 20–26-tool selection, not as a routing summary for something else to read.
3. The shared base prompt injected into all six roles' instructions, ahead of each role's own scope section, opened by claiming a specific identity ("Act as a principal-level RF … engineer") under the heading "# Principal RF Engineer" — and a correctly-routed specialist echoed it back as its own.

We decided to fix all three at once: pin `LOCAL_AGENT_MODEL`/`LOCAL_EXTRACTION_MODEL` to `qwen3.6:27b`, replace the five handoffs' descriptions with a new short, uniform, third-person `_ROUTING_SUMMARY` dict kept separate from each specialist's `domain_note`, and retitle the shared prompt file to "# RF Engineering Standards" with a reworded, role-neutral opening line.

## Considered options

### Model tag (`LOCAL_AGENT_MODEL` / `LOCAL_EXTRACTION_MODEL`)

**Keep `qwen3.8:27b` and wait for the upstream fix.** The crash's root cause is tracked upstream as `ollama/ollama#17778` and `#17812`, with a fix already written but unmerged as PR `#17813`. Rejected because there is no ETA on that merge landing in a released Ollama build, and this repo's routing is unusable in the meantime — waiting blocks real work for an indefinite, out-of-repo dependency.

**Route local traffic through Ollama's native `/api/chat` endpoint instead of the OpenAI-compatible one.** Considered because the crash is endpoint-specific behavior, not a defect in the model weights themselves. Rejected because `agent/main.py`'s local-provider path (and `knowledge/extraction_llm.py`'s) is built on the `openai-agents` SDK's `AsyncOpenAI`-shaped client throughout — talking to `/api/chat` instead would mean bypassing or forking the SDK's own request path for one provider only, a much larger and riskier change than swapping a model tag.

**Move to a different model family entirely (e.g. `gpt-oss:20b`, the code's own hard-coded fallback default).** Rejected because the reproduced crash is specific to this Qwen3 model file's chat template on this Ollama version, not to the Qwen3 family generally — abandoning the family throws away its agentic-task tuning to chase a bug that a same-family, same-size-class tag (`qwen3.6:27b`) already sidesteps, cleanly and with no other code change.

*A note on the citation itself, corrected after re-checking the primary sources directly:* the bug identity, exact error string, issue numbers, and unmerged-fix status are all confirmed by `ollama/ollama#17778`/`#17812`/PR `#17813`. But those upstream reports describe the failure on Ollama's *native* `/api/chat` endpoint (and inside the Ollama Desktop app's own internal web-search loop) — none of the three mention `/v1/chat/completions`, "OpenAI-compatible," `openai-agents`, or `AsyncOpenAI` by name. The direct evidence that `/v1/chat/completions` itself crashes under `qwen3.8:27b` is this repo's own live reproduction against its principal-role handoff routing, not the upstream issue text. The two are the same underlying defect (same model file, same missing-user-turn root cause, same error string) reproduced on two different doors into the same broken code path — but the ADR should say so accurately rather than imply the GitHub issues name this repo's specific endpoint, which they do not.

### Handoff tool descriptions (`route_to_<role>_role`)

**Keep reusing each specialist's `domain_note` verbatim as its handoff's tool-selection description (the design in place before this fix).** This produced five wildly uneven, pronoun-switching tool schemas — from roughly 400 characters (verification) to 2,500+ characters (antenna), several of them second-person text like "it takes over … You focus on …" written for the specialist itself, not for the principal choosing between five options. Rejected because it was live-tested and reliably recognized only the shortest one, `route_to_verification_role`; the other four went silently unselected regardless of how well they actually matched the question.

**Auto-truncate or auto-summarize each `domain_note` (e.g. first sentence, first N characters) rather than write new text.** Rejected because a `domain_note` isn't written to front-load a stable one-line summary — truncating one lands wherever its author happened to put a clause break or a caveat, not on a description of scope. Making that reliable would mean restructuring every `domain_note` around a truncation point anyway, which is more invasive than writing a dedicated summary once.

**Route by keyword/rule-based classification instead of model tool selection.** Considered because the failure is specifically a small local model's tool-selection reliability. Rejected because it steps outside the SDK's handoff mechanism entirely — losing the structured context transfer and tracing (`handoff_span`) the framework already provides — to solve a reliability problem that, per the fix below, was actually solvable by making the *descriptions* comparable, not by replacing the selection mechanism.

**Replace the five `handoff()`-built tools with one router tool keyed by a role enum — a single hand-built `Handoff` whose `on_invoke_handoff` resolves the target `Agent` dynamically from the parsed enum value.** Raised independently as an alternative design and checked against the actually-installed SDK rather than taken on faith: `on_invoke_handoff` genuinely supports returning any `Agent` dynamically (the SDK's own docstring names this as the intended extension point over dynamic destination selection), a hand-built `Handoff` still produces a real `handoff_span` and still transfers control within the same `Runner.run()` call, and the "Multiple handoffs requested" guard (`turn_resolution.py:588–596`) is keyed by how many handoff-shaped tool calls appear in one turn, not by tool identity — so this design would not reintroduce the earlier `.as_tool()` nested-call crash class the current handoff design was built to escape. It is deferred, not rejected: the current five-handoff design is live-tested (3-for-3, zero crashes, after the three fixes in this ADR) and the enum design has zero live-model testing in this repo. It targets a failure mode — a model confusing *many* similarly-shaped tool schemas — that is a real, documented history here but is not the failure that just recurred (that was five *unevenly*-shaped schemas, which the `_ROUTING_SUMMARY` fix addresses directly). See Consequences for the concrete conditions under which to build and live-test it.

### Shared base prompt identity (`prompts/principal_engineer.md`)

**Leave the file as-is — titled "# Principal RF Engineer," opening "Act as a principal-level RF … engineer" — and rely on each specialist's own `domain_note` to override it.** This is the state that produced the leak: a correctly-routed Test Engineer specialist's first reply said "I am the Principal RF Engineer" despite the handoff working exactly as intended. Rejected because the shared prefix's identity claim comes first in the instructions string, ahead of the specialist's own "## Role scope" section, and nothing in the specialist's `domain_note` explicitly contradicts a claim the specialist was never meant to have to contradict.

**Reorder the instructions string so each role's `domain_note` comes before the shared content, instead of after it.** Considered as a smaller change than rewording the shared file. Rejected because it treats the leak as a position/recency problem when it is a content problem: the shared prefix asserts a specific role identity that is simply false for five of the six roles reading it. Reordering doesn't remove the false claim, it only bets that a specialist notices and overrides it — the earlier evidence says that bet doesn't reliably pay off.

**Split the shared content into six separate, fully duplicated prompt files, one per role.** Rejected because the universal content — the evidence hierarchy, mandatory provenance labels, the 14-step workflow, the RF-checks list, numerical discipline, the design-review checklist, tracking-status behavior, and the safety-gating rules — is legitimately identical across all six roles by this repo's own design, and none of it was the source of the leak. Duplicating it six ways reintroduces exactly the drift-between-copies problem a single shared file exists to prevent, to fix a one-line identity claim.

**Retitle the shared file and reword its opening line to drop the role-identity claim, keep everything else (chosen).** "# Principal RF Engineer" became "# RF Engineering Standards"; "Act as a principal-level RF … engineer" became "Apply principal-level rigor to RF, microwave, antenna, electromagnetics, and RF-systems engineering work." — same standard of rigor demanded, no claim about *whose* rigor. Each role's own `domain_note` is now the sole source of identity: the principal's still opens "You are the coordinating principal-level reviewer," but that text lives only in the principal's own role spec, not in text every other role also receives.

## Consequences

All three fixes were validated together, live, against the real local backend: the routing design that crashed before is now 3-for-3 with zero crashes, and the specialist correctly identifies itself by role rather than echoing the principal's old identity. The wiring around decision 2 is also covered by four existing tests in `tests/test_agent_roles.py` — `test_principal_has_one_handoff_per_specialist_role`, `test_specialist_handoffs_registry_matches_specialist_keys`, `test_each_handoff_targets_the_correct_specialist_agent`, and `test_handoff_description_names_its_role` — though, as that file's own docstring is explicit about, these check the handoff *wiring* (right tool name, right target agent, right description content) and cannot exercise a live routed query themselves; this environment has no configured local LLM backend for automated tests to call, so the actual routing-accuracy verification is a live re-test outside the automated suite, same constraint this file has documented since the `.as_tool()`-to-`handoffs` migration.

Decision 2 has a known residual gap, not a regression: an independent accuracy check of the five `_ROUTING_SUMMARY` entries against each specialist's real tool list found two (`test`, `verification`) fully accurate on first pass, and the other three (`systems`, `microwave`, `antenna`) each missing one whole category of tools that specialist genuinely holds (systems' own IP3/IM3 linearity tools, microwave's filter-prototype synthesis, antenna's KiCad-PCB gerber2ems signal-integrity simulator) — since corrected in all three. None of the five ever *overclaimed* a capability its specialist lacks, so the failure mode this fix targets (a model unable to compare five wildly mismatched schemas) was closed even before that correction; the omissions were a documentation-completeness gap, not a functional one.

A second live-testing round after this ADR's fixes landed also surfaced a related-but-distinct failure mode this ADR does not close: on one of several live draws, the principal skipped routing to `systems` entirely for a cascaded-noise-figure question and computed the answer itself via unaided reasoning, then labeled the result `CALCULATED` — a provenance label this repo's own evidence-hierarchy rules reserve for a value verified by a deterministic tool, which the principal does not hold directly. Some run-to-run variation is expected (this model runs at temperature 1.0 in its reasoning mode, by design, per Qwen's own recommended setting), but a false `CALCULATED` label is a provenance-integrity problem independent of routing recall, and is tracked separately rather than folded into this ADR's scope.

Decision 1 makes this repo depend on a specific, currently-broken upstream model tag staying avoided rather than fixed: `qwen3.8:27b` remains unusable here until Ollama merges PR `#17813` (or an equivalent fix) into a released build, at which point it is worth re-testing whether the size-for-size swap back is still necessary or was only ever a stopgap.

Decision 2's deferred alternative — one router tool with a hand-built `Handoff` and an enum-resolved target, instead of five `handoff()` calls — should be revisited, not treated as closed, under two concrete triggers: (1) if a deliberately ambiguous, multi-domain routing query reproduces the old shortest-tool bias even against the new short, uniform `_ROUTING_SUMMARY` descriptions, that is direct evidence the schema-count failure mode is back regardless of description quality, and is the point to build and live-test the enum design for real rather than by analogy; (2) when a sixth specialist role is added, both the current design's per-tool maintenance burden (five hand-written descriptions with no test enforcing they stay uniformly shaped) and the enum design's own better-understood scaling story become concrete rather than hypothetical, and is the natural point to re-run this comparison against real data.

# microwave/antenna/test migrate fully onto the MCP-routed path

**Serves:** [#479](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/479), which superseded the narrower hybrid `tools=[...]` + `mcp_servers=[...]` split [#376](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/376) considered but did not attempt. Related: [#372](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/372)/[#475](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/475) (the hang and its fix), [#377](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/377) (the connection-lifecycle prerequisite this decision scales), [#477](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/477)/[#478](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/478) (disclosed gaps this decision changes the stakes of), [#316](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/316) (the parent MCP-migration tracking issue), and `docs/tool-registration-audit-2026-09-13.md` (an independently-run same-day audit that reproduced this decision's own tool counts exactly).

**Plain-language summary of what "MCP-routed" means here, for a reader outside RF/agent-infrastructure work:** this program's AI agent is split into six specialist roles (a principal engineer, a systems engineer, a microwave engineer, an antenna engineer, a verification engineer, and a test engineer). Each role needs a different subset of ~155 tools (calculators, solvers, document search, and so on). There are two ways to hand a role its tools: the old way bakes a Python function object for every tool straight into the agent process (`agent/main.py`'s wrapper layer), duplicating a tool's implementation for every role that uses it; the new way (MCP — Model Context Protocol) runs one real server process per role that serves each tool from a single, independent implementation (`mcp_server/server.py`), and the role just asks that server for whichever tools it's allowed to see. Three of six roles (principal, systems, verification) already made this switch. This decision is about whether the remaining three (microwave, antenna, test) — which hold the actual long-running solver tools (NEC2++, openEMS, HFSS, Elmer, MEEP, Palace, and others) — can make it too.

## Background

[#376](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/376) migrated principal/systems/verification fully onto MCP and deleted their now-dead wrapper functions. It explicitly left microwave/antenna/test on the old direct-call path, blocked by a Windows subprocess hang ([#372](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/372)) that a full migration attempt hit, and considered — but did not attempt — a hybrid split (keep the riskiest solver tools direct-attached, migrate the rest).

[#475](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/475) fixed the hang for an unrelated reason: it was never a blocked event loop, but a spawned solver subprocess inheriting the MCP server's own stdin handle, fixed with a single `isolate_transport_stdin()` function verified with true behavioral parity (150 s+ hang collapsing to 0.06–0.09 s, 8/8 parity tests). That removes the hybrid's original reason to exist and reopens the question this ADR answers: is a **full** migration — not just the hybrid — now viable?

## Investigation

The four points [#479](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/479) named were each answered with direct measurement against the real code, not a guess:

**1. Scaling `MCPServerManager` from 3 to 6 servers.** `agent/main.py`'s `run()` connects every role's server sequentially (`connect_in_parallel` defaults to `False`, and nothing in this repo ever sets it `True`), each server a fresh subprocess importing the whole `mcp_server.server` module (~2.0 s alone, dominated by module import, not handshake or process-launch overhead). Measured directly: 3 servers sequential ≈ 6.7 s, 6 servers sequential ≈ 14.0 s — a clean linear scaling matching the per-import cost. `MCPServerManager` already ships an unused `connect_in_parallel=True` flag: the same 6-server case measured 3.7 s with it on. Every query today is a one-shot CLI invocation (`run(query)`) with no persistent session and no chained handoffs, so a 14 s eager-connect tax mostly pays for five servers a given query never touches.

*In plain terms: connecting to all six specialist servers before answering even one question currently takes about 14 seconds, almost entirely from Python re-importing the same large module six times. Flipping on a switch the connection code already has, but nobody turns on, cuts that to under 4 seconds — a one-line change with no new design.*

**2. The mid-handoff-to-unconnected-role question.** Structurally unaffected by the role count: `run()` connects every server **before** the agent conversation starts, so a handoff can never land on a server that was never connected, whether there are 3 or 6. What is new at 6: three of those servers (microwave, antenna, test) now hold real long-running solver tools, so the shared manager's single `cleanup_all()` teardown, on an exception path, may now be walking away from a live 10-to-60-minute solve rather than an idle connection.

**3. [#477](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/477)/[#478](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/478)'s interaction with a live production path.** Both are real, already-disclosed, already-measured gaps — cancelling an MCP call doesn't kill the child solver subprocess ([#477](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/477)); one server answers nothing else while a tool call is mid-solve ([#478](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/478)) — found on servers that today hold **zero** of the 15 solver tools. Migrating microwave/antenna/test is what turns them from "measured on a synthetic reproduction, affecting nothing real" into "governs the actual solver calls this program's stated purpose depends on." Neither gap gets worse *in kind* from migrating — the old direct-call path has the identical synchronous-blocking behavior today, in the same interpreter thread, with no kill switch either — only worse in *stakes*.

**4. The ground-truth tool audit.** Read directly from the code (and independently reproduced the same day by `docs/tool-registration-audit-2026-09-13.md`): microwave holds 31 tools, antenna 27, test 24; their union is exactly 59, exactly equal to `agent/main.py`'s entire remaining `_ALL_TOOLS`. Every one of those 59 already has an independent `mcp_server/server.py` implementation. 14 are already served over MCP to an already-migrated role; the remaining cross-sharing among microwave/antenna/test themselves (touchstone/VSWR/return-loss/search tools shared by all three, 8 solver tools shared by antenna+test, 4 by microwave+test) is exactly why 59 tools, not 45, still need the wrapper today — and it stops being a complication, not a new one, once every role is on the same MCP path: a tool served once from `mcp_server/server.py` needs no dual home.

## Decision

**Go: migrate microwave/antenna/test fully onto the MCP-routed construction, in the same staged shape [#376](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/376)/[#377](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/377) already used for the first three roles**, not as one change but as this sequence:

1. Add `"microwave"`, `"antenna"`, `"test"` to `agent/mcp_roles.py`'s live-role handling; move their 59 tool-name lists from `agent/main.py`'s `ROLE_SPECS.tools` into `MIGRATED_ROLE_TOOL_NAMES`; replace their old-style `SPECIALIST_HANDOFFS` entries with `build_role_agent()` calls, mirroring how `systems`/`verification` are already built; then delete `_ALL_TOOLS`, its `assert_all_tools_categorized()` call site, and the now-dead `ROLE_SPECS.tools`/`ROLES` entries for these three — exactly the cleanup [#376](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/376) already did for the other 37 tools. Extend `tests/test_mcp_roles.py`'s wire-level round-trip assertions to all six roles and rewrite `tests/test_agent_roles.py` accordingly.
2. In the same change, turn on `connect_in_parallel=True` on the shared `MCPServerManager` — isolated, no architectural risk, and directly answers this ADR's own Point 1 finding (~14 s → ~3.7 s per query at 6 servers).
3. A live-model verification pass for at least one handoff into a migrated solver-holding role, matching the bar [#377](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/377) set for the first three (`tests/test_live_model_run.py`).
4. Schedule [#477](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/477) (kill the child subprocess on cancel/timeout) in the **same window** as step 1, not left indefinitely open — `cleanup_all()` walking away from a still-running solver child is a genuinely new interaction the current 3-role live path has never had to handle, since none of its three servers ever runs a real solve.
5. [#478](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/478) (worker-thread dispatch for responsiveness) can be scheduled independently, at lower urgency, given this repo's current one-shot, non-chained-handoff, no-persistent-session architecture.

Nothing in steps 1–5 is implemented under [#479](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/479) itself, which is an investigation-and-decision ticket only, per its own explicit out-of-scope note; steps 1, 2, 3 and 5 above are filed together as [#573](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/573) (broken out there into its own seven concrete sub-steps), and step 4 ([#477](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/477)) is scheduled in the same window but tracked as its own pre-existing ticket.

## Considered and rejected

- **Leave microwave/antenna/test on the old wrapper path indefinitely.** Rejected: the hang that stopped the prior attempt is genuinely fixed and independently re-verified in this investigation; nothing new was found that blocks a full migration, and leaving 59 tools duplicated across two registration surfaces is exactly the drift [#316](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/316) exists to close.
- **The hybrid split [#376](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/376) considered** (keep ~13–15 solver tools direct-attached, migrate the rest). Rejected: its whole reason to exist was routing around the [#372](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/372) hang, which no longer applies, and it would leave the cross-role tool-sharing complication this investigation found a full migration actually *resolves* rather than manages.
- **Build genuine lazy, connect-on-first-handoff server startup**, rather than the flat `connect_in_parallel=True` switch. Rejected for this decision: [#377](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/377)'s own investigation already established there is no SDK hook firing on handoff selection, so real laziness needs hand-built, unscoped plumbing. `connect_in_parallel=True` is a one-line change already available in the installed SDK and cuts the measured 6-server cost by roughly 4x with no new architecture; lazy connection remains an option for later if per-query latency still matters after that.

## Consequences

- Three followers of this decision are separately ticketed rather than bundled here: the migration implementation itself ([#573](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/573), step 1), the `connect_in_parallel=True` flip (folded into the same PR as #573, step 2), and [#477](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/477)'s subprocess-kill fix (step 4, scheduled in the same window).
- Once the migration lands, `agent/main.py`'s wrapper layer — `_ALL_TOOLS`, its `assert_all_tools_categorized()` call site, and the `ROLE_SPECS.tools` literals for microwave/antenna/test — becomes fully deletable; no tool in this program will need two independent registrations after that.
- [#477](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/477) and [#478](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/478) remain open, disclosed gaps, not blockers — per this program's own "warn, never block" doctrine — but their consequence changes materially once real, long, resource-consuming solver subprocesses sit behind the path they describe, which is why [#477](https://github.com/parthalon025/Principle_RF_Engineer_Agent/issues/477) is pulled into the same window as the migration rather than left at its current priority.
